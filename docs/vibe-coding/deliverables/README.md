# Vibe Coding 产研交付文档体系

这套体系不按部门讲理论，而是按项目真正需要的文档推进。每份文档只解决一类问题，并有唯一事实源，避免同一规则在多处写出不同版本。

## 文档顺序

| 顺序 | 文档 | 回答的问题 | 主责 | 下游使用者 |
|---|---|---|---|---|
| 1 | [PRD](./01-PRD.md) | 做什么、为什么、怎样算完成 | 产品/业务 | 全员 |
| 2 | [交互与页面说明](./02-UX-SPEC.md) | 用户怎么操作、每种状态看到什么 | 产品 | 前端、测试 |
| 3 | [技术方案](./03-TECH-SOLUTION.md) | 怎么实现、影响哪里、风险是什么 | AI/研发 | 开发、测试、发布 |
| 4 | [数据库设计](./04-DATABASE-DESIGN.md) | 数据如何保存、关联和升级 | AI/研发 | 后端、测试、运维 |
| 5 | [接口文档](./05-API-SPEC.md) | 前后端如何按同一契约通信 | AI/研发 | 前端、后端、测试 |
| 6 | [开发实施计划](./06-DEVELOPMENT-PLAN.md) | 以什么顺序拆任务并交付 | AI/研发 | 产品、开发 |

## 唯一事实源

- 业务目标、范围、规则、优先级和验收标准只以 PRD 为准。
- 页面结构和交互状态以交互说明为准，但不得改变 PRD 业务规则。
- 架构、依赖、安全、性能和部署决策以技术方案为准。
- 字段、关系和数据生命周期以数据库设计为准。
- 请求与响应字段、错误码和鉴权以接口文档为准。
- 测试方案不能重新发明需求，只能把 PRD 验收标准转成可执行用例。
- 任何已确认内容发生变化，先更新所属文档并记录变更，再改代码。

## 最小使用方式

演示版至少完成 PRD、简版技术方案和测试验收；业务版完成全部文档；商用版还要补齐安全、性能、四套环境、灰度、监控、备份和回退内容。
